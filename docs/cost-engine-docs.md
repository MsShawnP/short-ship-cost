# Cost Engine Documentation

Reference for whoever consumes the order and cost data — typically the
interactive tool. Covers the three SQLite databases, every table in
the cost DB, how to join across them, what each cost dimension
measures and how it's computed, how the buffer simulation works, and
the known limitations.

Generated 2026-05-07 against the current materialized state.

---

## 1. Database inventory

Three SQLite files under `data/`:

### `data/cinderhaven_extract.db` — reference data

Read-only, derived once from the upstream `cinderhaven-data` repo's
built database. Nine tables.

| Table | Rows | What it is |
|---|---:|---|
| `product_master` | 50 | SKU master: identifiers, product line, case pack, MSRP, nutrition. Some rows carry deliberate data-quality defects (missing case dimensions, etc.) |
| `sku_costs` | 50 | Per-unit COGS, landed cost, retailer-specific wholesale prices (incl. KeHE), channel trade-spend rates |
| `stores` | 903 | Retail door list (Walmart, Costco, WF, regional chains) plus aggregated rows for UNFI, KeHE, DTC |
| `distribution_log` | 12,565 | SKU × store authorization history with auth and deauth dates |
| `promotions` | 198 | Retailer-specific promo events |
| `price_history` | 398 | Time-keyed wholesale price changes by SKU × retailer |
| `chargebacks` | 381 | Historical compliance chargebacks (data-quality and shipment) — **not the rate schedule the cost engine uses** |
| `retailer_rules` | 90 | Per-(retailer, deduction_type) rules: dispute windows, auto-deduction, evidence requirements, typical recovery rates |
| `sku_velocity` | 50 | Derived rollup from upstream `scan_data`: `avg_weekly_units`, `total_annual_units`, `velocity_rank` |

### `data/short_ship_orders.db` — generated order data

Six tables generated by the scripts in `scripts/`. This is the data
the cost engine reads.

| Table | Rows | What it is |
|---|---:|---|
| `orders` | 74,306 | One row per order (retail/distributor/DTC). Carries `retailer`, `channel_type`, `order_date`, `due_date`, `ship_date`, `delivery_location`, `order_type` |
| `order_lines_original` | 272,352 | Original order lines as the customer submitted them — `quantity_ordered`, `unit_of_measure` (case/unit), `unit_price` |
| `order_lines_shipped` | 272,352 | What actually shipped after triage. Same line count as original (one-to-one); `quantity_shipped <= quantity_ordered`. Carries `original_line_id` for trace |
| `order_shorts` | 45,902 | One row per shorted retail/distributor line, with reason. DTC drops are not represented here |
| `dtc_outcomes` | 59,624 | One row per DTC order. `hold_start_date`, `resolution`, `resolution_date`, `days_held` |
| `distributor_returns` | 48 | Returned and claimed product on UNFI/KeHE promo orders |

### `data/short_ship_cost.db` — cost engine output

Nine tables produced by `scripts/cost_engine/`. This is what the
interactive tool reads.

| Table | Rows | What it is |
|---|---:|---|
| `cost_summary` | 8 | One row per cost dimension with the headline total |
| `cost_by_retailer` | 33 | Cost per (dimension, retailer) |
| `cost_by_sku` | 404 | Cost per (dimension, sku) — every contributing SKU, not just top-N |
| `cost_by_month` | 160 | Cost per (dimension, month) for time-series charts |
| `deauthorization_events` | 127 | Detailed log of each deauth event with trigger evidence |
| `cost_parameters` | 26 | Every tunable parameter: rates, thresholds, margins, labor costs |
| `buffer_scenarios` | 4 | One row per buffer-simulation scenario (target fill rates 80/85/90/95%) |
| `buffer_scenario_details` | 32 | Per-scenario × per-dimension cost recovery |
| `buffer_deauth_recovery` | 241 | Which deauth events are avoided at each fill-rate scenario |

## 2. Table schemas in `short_ship_cost.db`

All cost columns are USD. All `_pct` columns are percentages on a
0–100 scale (not 0–1).

### `cost_summary`

| Column | Type | Notes |
|---|---|---|
| `dimension` | TEXT, PK | One of the 8 cost dimensions (see §4) |
| `total_cost` | REAL | Total dollar cost across the 3-year window |
| `pct_of_shipped_revenue` | REAL | `total_cost / shipped_revenue × 100` |
| `description` | TEXT | One-paragraph human explanation of what the row measures |

### `cost_by_retailer`

| Column | Type | Notes |
|---|---|---|
| `dimension` | TEXT | FK → `cost_summary.dimension` |
| `retailer` | TEXT | Reporting channel name. Regional chains are collapsed to `Regional`; DTC stays `DTC` |
| `cost` | REAL | Dollar cost for this dimension at this retailer |

PK is (`dimension`, `retailer`). Sums per dimension reconcile to
`cost_summary.total_cost`.

### `cost_by_sku`

| Column | Type | Notes |
|---|---|---|
| `dimension` | TEXT | FK → `cost_summary.dimension` |
| `sku` | TEXT | FK → `product_master.sku` |
| `cost` | REAL | Dollar cost for this dimension on this SKU |

PK is (`dimension`, `sku`). Some dimensions (e.g., `triage_labor`)
have no SKU attribution and contribute zero rows here. Sums per
dimension are `<=` `cost_summary.total_cost`.

### `cost_by_month`

| Column | Type | Notes |
|---|---|---|
| `dimension` | TEXT | FK → `cost_summary.dimension` |
| `month` | TEXT | `YYYY-MM` |
| `cost` | REAL | Dollar cost for this dimension in this month |

PK is (`dimension`, `month`). Sums per dimension reconcile to
`cost_summary.total_cost` for dimensions that have monthly
attribution; `deauthorization` does not (events are SKU/retailer-
level, not monthly).

### `deauthorization_events`

| Column | Type | Notes |
|---|---|---|
| `sku` | TEXT | FK → `product_master.sku` |
| `retailer` | TEXT | Walmart, Costco, Whole Foods, UNFI, KeHE, or one of the regional chains |
| `trigger_type` | TEXT | `velocity_below_threshold` or `distributor_consecutive_months` |
| `velocity_without_shorts` | REAL | Units/store/week if shorts had shipped (velocity-trigger only) |
| `velocity_with_shorts` | REAL | Actual units/store/week as shipped (velocity-trigger only) |
| `threshold` | REAL | Retailer's velocity threshold (velocity-trigger) or 0.90 (distributor) |
| `fill_rate` | REAL | Lowest monthly fill rate observed (distributor-trigger); overall fill (velocity-trigger) |
| `consecutive_months_below_threshold` | INTEGER | 3 for distributor-trigger, NULL for velocity-trigger |
| `annualized_revenue_lost` | REAL | 12-month revenue at risk for this (sku, retailer) pair |

PK is (`sku`, `retailer`, `trigger_type`).

### `cost_parameters`

| Column | Type | Notes |
|---|---|---|
| `name` | TEXT, PK | Parameter key (e.g., `otif_walmart_rate`) |
| `value` | REAL | Numeric value |
| `unit` | TEXT | `fraction`, `USD`, `USD/hour`, `units/store/week`, `minutes`, `months` |
| `basis` | TEXT | What the rate applies to (e.g., `COGS`, `shorted goods value`) |
| `level` | TEXT | `PO`, `PO line`, etc. (where applicable) |
| `description` | TEXT | Human explanation |
| `source` | TEXT | Where the parameter came from (doc reference or PLAN task) |

The interactive tool should read these for default values and let
users override before re-computing.

### `buffer_scenarios`

| Column | Type | Notes |
|---|---|---|
| `target_fill_rate` | REAL, PK | Scenario target (0.80, 0.85, 0.90, 0.95) |
| `actual_fill_rate_achieved` | REAL | Achieved fill after the per-line lift (slightly above target due to asymmetric clamp) |
| `total_cost` | REAL | Total cost of shorts under this scenario |
| `total_recovery` | REAL | `baseline_total - simulated_total` |
| `recovery_pct` | REAL | `total_recovery / baseline_total × 100` |

### `buffer_scenario_details`

| Column | Type | Notes |
|---|---|---|
| `target_fill_rate` | REAL | FK → `buffer_scenarios.target_fill_rate` |
| `dimension` | TEXT | FK → `cost_summary.dimension` |
| `original_cost` | REAL | Baseline value of this dimension |
| `simulated_cost` | REAL | Value at this scenario |
| `recovery_amount` | REAL | `original_cost - simulated_cost` |
| `recovery_pct` | REAL | Per-dimension recovery percentage |

PK is (`target_fill_rate`, `dimension`). 4 scenarios × 8 dimensions
= 32 rows.

### `buffer_deauth_recovery`

| Column | Type | Notes |
|---|---|---|
| `target_fill_rate` | REAL | Scenario |
| `sku` | TEXT | FK → `product_master.sku` |
| `retailer` | TEXT | |
| `trigger_type` | TEXT | `velocity_below_threshold` or `distributor_consecutive_months` |
| `original_status` | TEXT | Always `deauthorized` |
| `simulated_status` | TEXT | Always `avoided` |

PK is (`target_fill_rate`, `sku`, `retailer`, `trigger_type`). One
row for every deauthorization event that disappears at a given
scenario fill rate.

## 3. Join paths

The three databases connect through stable IDs:

```
cinderhaven_extract                   short_ship_orders                  short_ship_cost
-------------------                   ------------------                 ----------------
product_master.sku  <----.            orders.order_id <-.                cost_by_sku.sku
                          \                              \               cost_by_retailer.retailer
sku_costs.sku       <-----+----  order_lines_original.{order_id, sku}    cost_by_month.month
                          /                                              deauthorization_events.{sku, retailer}
sku_velocity.sku    <----'           order_lines_shipped.{order_id, sku} buffer_*.target_fill_rate
                                                                         cost_summary.dimension
stores.{retailer, store_id}  --  orders.{retailer, delivery_location}

distribution_log.{sku, store_id, authorized_date, deauthorized_date}  --  filters orders
```

**Working with all three**: open the cost DB, attach the others.

```sql
ATTACH DATABASE 'data/cinderhaven_extract.db' AS ext;
ATTACH DATABASE 'data/short_ship_orders.db' AS ord;

SELECT cs.dimension, cs.total_cost,
       cr.retailer, cr.cost AS retailer_cost
FROM cost_summary cs
JOIN cost_by_retailer cr ON cr.dimension = cs.dimension
ORDER BY cs.total_cost DESC, cr.cost DESC;
```

**Tracing a cost back to specific orders**: a deauth event for
(CHP-0071, Walmart) traces back through `order_lines_shipped` and
`orders` to every Walmart line of that SKU.

```sql
SELECT o.order_id, o.order_date, lo.quantity_ordered, ls.quantity_shipped
FROM ord.orders o
JOIN ord.order_lines_original lo ON lo.order_id = o.order_id
JOIN ord.order_lines_shipped ls  ON ls.original_line_id = lo.order_line_id
WHERE o.retailer = 'Walmart' AND lo.sku = 'CHP-0071'
ORDER BY o.order_date;
```

## 4. Cost dimensions

Each of the eight rows in `cost_summary` is computed by an
independently testable module under `scripts/cost_engine/`. The
parameter names below are keys into `cost_parameters`.

### `lost_revenue` — **$18.7 M (36.1% of shipped revenue)**

The base gap. Lost dollars on retail and distributor lines:
`(quantity_ordered − quantity_shipped) × case_pack_qty × unit_price`.
DTC cancellation losses are *not* in this dimension — they're in
`dtc_cancellations` to avoid double-counting. No parameters; this is
a direct sum.

### `otif_fines` — $826 K (1.6%)

Retailer-specific fines per the schedule in
`docs/cost-engine-benchmarks.md`:
- Walmart: 3% of line COGS, **per non-compliant PO line** (line fill < 98%). Parameter `otif_walmart_rate`.
- Costco: $250 flat per PO with any short. Parameter `otif_costco_flat_fee`.
- Whole Foods: 2% of PO COGS when PO fill < 95%. Parameter `otif_whole_foods_rate`.
- UNFI: 3% of **shorted goods value** when PO fill < 95%. Parameter `otif_unfi_rate`. (Different basis than the others.)
- KeHE: 2% of PO COGS when PO fill < 95%. Parameter `otif_kehe_rate`.
- Regionals: 1% of PO COGS when PO fill < 90%. Parameter `otif_regional_rate`.
- DTC: no fines.

PO-level fines are attributed to SKUs by demand-share; UNFI's
shorted-value fine is attributed by each line's share of shorted
value; Costco's flat fee is attributed to the worst-shorted SKU on
the PO.

### `chargebacks` — $75 K (0.2%)

Estimated retailer chargebacks beyond OTIF, applied to shorted goods
value:
- Walmart, Costco: 0.5% of shorted goods value. Parameter `chargeback_rate_walmart_costco`.
- Other retailers: 0.3%. Parameter `chargeback_rate_other`.

The Cinderhaven `chargebacks` historical table is not used because
those rows reflect data-quality and shipment chargebacks unrelated to
the synthetic shorts we generated.

### `deauthorization` — $5.86 M (11.3%)

Forward-looking revenue at risk from short-caused deauthorizations.
Two trigger mechanisms:

- **Velocity-based** (Walmart, Costco, Whole Foods, regional chains): if
  velocity-without-shorts crosses the retailer's threshold but
  velocity-with-shorts falls below, the short pushed the SKU below
  the delist line. Thresholds (units/store/week): Walmart 2.00
  (`deauth_velocity_walmart`), Costco 5.00 (`deauth_velocity_costco`),
  WF 1.50 (`deauth_velocity_whole_foods`), Regional 1.00
  (`deauth_velocity_regional`).
- **Distributor-based** (UNFI, KeHE): if monthly fill rate stays below
  90% (`deauth_distributor_fill_rate`) for 3+ consecutive months
  (`deauth_distributor_consecutive_months`), the SKU is delisted at
  that distributor.

Cost per event = 12 months annualized revenue
(`deauth_revenue_horizon_months`) for the (sku, retailer) pair = total
3-year revenue / 3.

### `dtc_cancellations` — $50 K (0.1%)

Full lost order value for DTC orders with
`resolution = 'cancelled_by_customer'`. Hold-for-complete means
nothing shipped, the whole order is lost. Parameters
`dtc_cancel_under_3_days` / `dtc_cancel_3_to_7_days` /
`dtc_cancel_7_to_14_days` / `dtc_cancel_over_14_days` drove the data
generation but don't enter the cost calculation directly here — this
module just sums the realized cancellations.

### `dtc_margin_leakage` — $5 K (~0.01%)

When a DTC customer abandoned a held order and bought in-store
instead (`resolution = 'purchased_in_store'`), the brand still earned
wholesale margin (~35%) on the in-store purchase but lost the spread
to DTC margin (~55%). Cost per order =
`order_value × (dtc_margin_pct − wholesale_margin_pct)` = `order_value × 20%`.

### `distributor_returns` — $24 K (0.05%)

Sum of `credit_amount` from the `distributor_returns` table —
returned-unsold and claim-filed product on UNFI/KeHE promo orders.
Generated at 12% (`distributor_unsold_promo_rate`) and 5%
(`distributor_claim_filed_rate`) of shipped promo cases.

### `triage_labor` — $39 K (0.07%)

Manual order-edit labor on retail/distributor orders.
`triage_minutes_per_order × triage_hourly_rate / 60 ×
triage_share_of_orders × order_count` = `20 × 30 / 60 × 0.90 × 4,318
= $38,862`. DTC orders are excluded — they go through automated
fulfillment with no human edit. Triage labor stays flat across all
buffer scenarios because the process doesn't go away when fill rates
improve, only the outcomes change.

## 5. Buffer simulation

The simulation answers "what would even modest fill-rate improvement
save?" — framed as fine avoidance and cost recovery, not production
planning. Implementation in
`scripts/cost_engine/buffer_simulation.py`.

### How the simulation runs

For each target fill rate (80%, 85%, 90%, 95%):

1. Copy `short_ship_orders.db` to a temp file.
2. Lift `quantity_shipped` on each retail/distributor line:
   `new = max(current_shipped, round(qty_ordered × target_fill))`,
   capped at `qty_ordered`. Lines already above target stay; lines
   below get raised to target. Channel averages land slightly above
   target (asymmetric clamp).
3. Flip a fraction of cancelled DTC orders back to `shipped_complete`.
   Fraction = `1 − (1 − target) / (1 − current_fill)`. Modeling that
   better unit availability reduces hold time and cancellations.
4. Update `order_shorts` to match the new `quantity_shipped`.
5. Monkey-patch `cost_engine.common.ORDERS_DB` to point at the temp
   file, run all eight dimension modules, restore the path, delete
   the temp file.
6. Record results in `buffer_scenarios`, `buffer_scenario_details`,
   `buffer_deauth_recovery`.

The existing dimension modules and `short_ship_orders.db` are
**never modified**.

### Reading the results

```sql
-- Headline recovery per scenario
SELECT target_fill_rate, total_cost, total_recovery, recovery_pct
FROM buffer_scenarios ORDER BY target_fill_rate;

-- Per-dimension recovery at the 95% scenario
SELECT dimension, original_cost, simulated_cost, recovery_amount, recovery_pct
FROM buffer_scenario_details WHERE target_fill_rate = 0.95
ORDER BY recovery_amount DESC;

-- Which deauth events disappear at each fill rate?
SELECT target_fill_rate, COUNT(*) AS events_avoided
FROM buffer_deauth_recovery GROUP BY target_fill_rate
ORDER BY target_fill_rate;
```

### Identity at current fill

Running the simulation with `target_fill_rate <= current_fill_rate`
(currently 73.4%) is a no-op by design — both `recover_retail_shorts`
and `recover_dtc_outcomes` short-circuit. The output reproduces the
baseline within $1 per dimension. This is verified in
`scripts/validate_cost_engine.py`.

## 6. Known limitations

These are honest items the interactive tool should surface or work
around, not bugs to fix:

### OTIF stickiness at Walmart

OTIF fines drop only ~38% at the 95% scenario, not "near zero" as one
might expect. The reason is structural: Walmart's OTIF threshold is
**98%**, applied per PO line. Lifting lines to 95% leaves them
non-compliant, so per-line fines persist. To eliminate Walmart fines
we'd need a 98%+ scenario. Worth adding one if the tool needs that
view.

### Deauth noise at the 85% scenario

The 85% scenario shows a tiny *negative* recovery on
`deauthorization` (-1.7%, ~$100K on $5.86M). This is binary-
threshold noise — a few SKU/retailer pairs flip across the velocity
threshold either way as the per-line lift random-walks through
boundary cases, plus the random DTC sampling differs scenario-to-
scenario. The 90% staircase result is the dominant signal and is
clean. Could be flattened by averaging multiple seeds; doesn't
affect the headline narrative.

### Distributor returns flat across scenarios

`distributor_returns` doesn't change across the 80/85/90/95%
scenarios. By construction: returns are a property of *shipped promo
cases*, and the simulation lifts shipped quantities, so promo
shipped volume rises slightly but the rate (12% / 5%) stays fixed.
The interactive tool should explain this rather than claim
distributor returns are immune to fill-rate improvement — at higher
fill, promo shipments are larger, so absolute returns would actually
*increase*, but the cost engine reports the as-generated returns
without re-rolling the binomial draws per scenario.

### Triage labor flat across scenarios

By design — see §4. Triage process runs whether the outcome is good
or bad, so the labor cost is invariant to fill rate. The user spec
explicitly required this behavior.

### Two late-launch SKUs without orders

CHP-0054 and CHP-0067 were authorized in the final 5–6 weeks of the
window with very low brand-wide velocity. They have zero orders and
therefore zero contribution to any cost dimension. Realistic, not a
defect — recently-launched slow-movers wouldn't show up much in 5
weeks of demand history.

### KeHE pricing

`sku_costs` has a native `wholesale_kehe` column from upstream. KeHE
orders are priced using this column directly.

### Walmart "DCs" synthesized

The upstream `stores` table has no DC dimension, so Walmart orders
are placed at the (region, state) level (43 distinct DC equivalents)
rather than at true DC granularity. Adequate for the cost story.

### Chargebacks use fallback rates, not the historical table

The `chargebacks` table in the Cinderhaven extract is historical
actuals driven by data-quality issues unrelated to short-shipping.
The cost engine uses fallback rates (0.5% / 0.3%) flagged in the
module description.

### Buffer simulation per-line lift, not per-PO recovery

The simulation lifts every line proportionally rather than
prioritizing POs that would cross compliance thresholds with small
recovery (the OTIF-bumpable optimization). The current approach
produces the right channel-level fill targets but doesn't *minimize*
fines for a given recovery amount. A smarter recovery rule could be
swapped in without changing the rest of the engine.
